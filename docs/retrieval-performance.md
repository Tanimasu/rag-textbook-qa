# 本机重排性能与可选配置

本轮使用本机离线模型和已发布索引的临时副本，关闭 LLM、HyDE、引用核对和远程回退。
没有重建或修改原索引，也没有减少候选：Top 5 单本重排 15 条，全库每本取 15 条、五本合并 75 条后重排一次。
这些检查衡量延迟和排名一致性，不是回答质量验收。

## 口径

- 先用 `scripts/benchmark_retrieval.py --device mps --repeats 3` 跑五本教材各自首道开发题，单本、全库各 15 次。
- 参数筛选只用 dev 35 题，两种范围各检索一遍；逐题保存融合候选身份、正文 SHA-256 和 Top-5。
- batch、最大输入长度、精度和查询分词缓存分别改变，不叠加后再把收益归给单一因素。
- 中位数和 p90 均是描述性数字，p90 取最近秩 `ceil(0.9*n)`；测量排除模型加载，MPS 前后同步，不使用推理结果缓存。
- 全题确认只在方案冻结后执行一次。已知汉明码跨进程变化单列，不能把它算作某个重排配置的收益或回退。

当前 `bge-reranker-base` 实际最大输入长度为 **512 tokens**，默认 float32。
5700 个索引片段正文的字符长度中位数 446、p90 为 788、最大 8640；
token 长度（含正文特殊符号，不含问题）中位数 278、p90 为 503、最大 4074。
449 / 1969 / 3011 个正文分别超过 512 / 384 / 256 tokens；实际问题与正文配对后更容易触发截断。
因此缩短最大长度可能省时，也可能丢掉模型本来能看到的正文，必须单独验证排名。

## 开发集逐项筛选

每项 35 题，每题每范围各一次（单轮筛选）；除所列项外保持 batch 32、原生长度 512、float32。
全部候选身份和顺序均与基线一致。单轮顺序运行会受设备状态影响，耗时差不能单独当作严格因果收益。

| 方案 | 单本中位数 / p90（秒） | 全库中位数 / p90（秒） | 单本 / 全库 Top-5 变化题数 |
|---|---:|---:|---:|
|基线：batch 32 / 512 / float32|1.089 / 1.396|4.279 / 5.534|0 / 0|
|仅 batch 8|0.821 / 1.014|3.658 / 4.323|0 / 0|
|仅 batch 16|1.143 / 1.640|3.930 / 5.838|0 / 0|
|仅 batch 64|1.029 / 1.293|4.794 / 5.629|0 / 0|
|仅长度 384|0.642 / 0.903|2.964 / 3.719|23 / 22|
|仅长度 256|0.383 / 0.405|1.777 / 1.906|28 / 28|
|仅复用本次问题分词|0.820 / 0.928|3.135 / 3.771|0 / 0|
|仅 float16|0.334 / 0.430|1.292 / 1.488|4 / 4|

默认方案仅采用 **MPS 自动 batch 8**；CPU/CUDA 仍为 32，已有显式配置优先。
长度 384 / 256 和 float16 均有排名变化，保持默认关闭；没有用较少候选换速度，也没有依据 holdout 调参。
以上长度、精度是各自配合 batch 32 的单项结果；与 batch 8 叠加的组合不能套用这些数字。

## 配对计时与全题确认

五本首道开发题、每题每范围 **3 次**，同一进程交替 batch 32 和自动 batch 8；
每组每范围各 15 个样本，逐位 Top-5 零变化。两组均每次一次 embedding、一次重排，单本 15 / 全库 75 条候选。

| 范围 | batch 32 中位数 / p90（秒） | batch 8 中位数 / p90（秒） |
|---|---:|---:|
|单本|0.803 / 0.850|0.567 / 0.731|
|全库|3.250 / 3.419|2.789 / 2.937|

全库中位数约降低 14%。这些是本机小样本观察，不是跨设备或线上延迟保证。
最初按要求分开进程各跑 3 次的数字也保留：单本 0.617 / 0.675 → 0.557 / 0.721 秒，
全库 2.170 / 2.497 → 2.700 / 2.884 秒，**这份分开运行的全库数字反而变慢**。
因此没有把分开进程的差值当优化收益，额外用同进程交替配对核对运行状态的影响。

方案冻结后只做了一次 65 题配对确认，每题每范围每组一次：单本、全库的候选身份、顺序和 Top-5
均 **0/65 变化**，包括汉明码题，本轮无需排除任何一题。单本中位数 / p90 为
0.846 / 0.909 → 0.675 / 0.866 秒，全库为 3.421 / 3.876 → 3.008 / 3.410 秒。
这轮有其他本机检查并行，主要用于排名确认，发布的主要性能数字采用上面的独立配对开发题计时。
同一引擎的配对确认 **不证明跨进程抖动已经修复**，原有 Chroma 限制继续适用。

分词复用的整轮耗时看似更快，但仅测分词本身（35 题、30 轮、比较全库重复 5 次与复用一次）时，
中位数仅省 **0.124 毫秒**、p90 省 0.185 毫秒，不能解释秒级差值；没有据此新增默认缓存状态。

`baseline-sample.json` / `after-sample.json` 保存分开运行的原始结果，`screen.json` 保存逐项筛选，
`decision.json` 在全题确认前冻结选择和源码摘要，`paired-sample.json` 保存配对计时，
`final-all.json` 保存唯一一轮全题确认，`token-cost.json` 保存分词微测。

## 配置和边界

`RAG_QA_RERANK_BATCH_SIZE` 调整批大小，不设时由实际设备选择（MPS 8，CPU/CUDA 32），显式值优先。它只分批处理原有候选，不改变候选数量或顺序，
不改变模型指纹；在未验证过的设备上仍应自行计时。

以下开关默认关闭，只适用于 `local` 后端：

```env
# Reproduce one screened override at a time with batch 32.
RAG_QA_RERANK_BATCH_SIZE=32
# RAG_QA_RERANK_MAX_LENGTH=384
# RAG_QA_RERANK_DTYPE=float16
```

不设最大长度时沿用模型原生值；不设精度时保留 float32。float16 需要 MPS 或 CUDA，
CPU 和自动选中 CPU 都会明确报错。非默认长度、精度写进 provider 身份和指纹；
不带覆盖项的默认身份保留旧指纹兼容性，embedding 指纹不变。

remote 客户端和 `worker serve` 均拒绝这些长度/精度覆盖项，避免与 Worker 或本地回退静默混用。
默认 Worker 行为保持原样；若注入了不同配置的 Worker provider，客户端在健康检查时拒绝指纹不一致。
HTTP 传输检查使用本机模拟器，不连接真实远程 Worker。

## 复现与产物

激活 Conda `rag-textbook-qa`，并设置：

```bash
export RAG_QA_COMPUTE_BACKEND=local RAG_QA_DEVICE=auto
export HF_HUB_OFFLINE=1 TRANSFORMERS_OFFLINE=1
python scripts/benchmark_retrieval.py --device mps --repeats 3 --output <新产物目录>/baseline.json
# --questions dev expands the sample to every development question.
# --questions all is reserved for one final confirmation, never parameter selection.
```

脚本支持独立指定 `--reranker-batch-size`、`--reranker-max-length`、`--reranker-dtype`，
报告包括指纹、逐题教材/片段 ID/正文摘要、候选数量、provider 调用次数、耗时、中位数和 p90。
`--compare-batch-size 32` 在同一引擎上交替比较批大小；与历史引擎比较的 `--baseline-ref` 不能同用。
原始筛选脚本及报告在忽略目录 `artifacts/evaluations/reranker-performance-20261113/`。
