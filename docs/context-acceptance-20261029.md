## 4. 评测器实现与语义校准

### 确认并修复的实现问题

1. **来源编号与实际资料块没有绑定**：原实现只检查 `content in context`，交换两份来源的编号仍通过，随后 `context_blocks` 按编号取到另一份正文。`source-binding-before.json` 保存原输入和错误接受；修复后拒绝交换、缺失/多余块和重复编号，并保持来源清单可以重排，见 `source-binding-after.json` 及新增回归。五组真实历史 cases 仍能通过新输入验证，没有改写它们。
2. **近似摘录可能接受关键文字改动**：原 90% 匹配接受 `1023→1024`、否定字删除；归一化还会抹掉小数点或数字负号。现在保护数字、小数点/正负号、拉丁术语/符号及匹配范围内常见中文否定字，保留一般格式与少量普通文字容差。`evaluator-boundary.json` 保存原复现，`quote-guard-final.json` 的五组改动均被拒绝，原句均被接受；测试也覆盖符号 `t_c/t_m`。这不是完整数学解析或语义等价判定。
3. **无编号旧式上下文的兼容路径会异常**：`context_blocks` 对空标记列表仍构造一个结束位置，严格 zip 抛错。通过 HEAD 源码复现，见 `unnumbered-context-before.json`；修复并增加纯正文兼容回归。

接受输入/摘录的条件已改变，`JUDGE_VERSION` 从 **6 升为 7**；版本 6 及更早目录不可原地续跑。原始结果、评分和模型请求均未修改。README 去掉了“每个结论都标注出处”的保证式表述，使用说明与本地验收说明同步版本和能力边界。产品默认提示词未改变。

### 现行保护与能力边界

- 来源绑定、每条核证摘录必须匹配其声明 `source_id`、严格 JSON 重复键/非有限值拒绝、正常 `finish_reason=stop`、冻结输入/提示词/模型参数/版本隔离与旧版拒绝续跑，均由已有有意义回归加新增用例实际执行。
- “严格 JSON”指对象内部无歧义和数值合法；解析器仍按设计兼容代码围栏/对象外说明文字，不宣称整个响应必须是裸 JSON。
- 摘录匹配是文字检查，仍不能证明陈述的条件、范围、因果与原文一致。
- **当前生成评判器不衡量回答指定引用的完整性**：拆分提示词明确去掉回答引用号，核证可从全部来源找支持。即使来源输入绑定正确，回答错引 3、评判找到来源 2，也能获得支持标签。`evaluator-boundary.json` 保存这一可执行边界。本轮逐主张引用复核是单独证据，不能用 `problem_claims` 代替。
- 缺失、超时、无效评分不计作通过。`stored` 仅说明输入为存档，不补证其历史生成正常结束。
