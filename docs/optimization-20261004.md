# 2026-10-04 可靠性与检索优化

## 已完成的改动

- 教材索引增加发布版本；旧索引通过集合 UUID 和写入位置识别更新。
  BM25 正文、编号和元数据一起替换，相邻片段缓存随之清空。
  检索跨越一次索引发布时重试，避免一次回答混用两代资料。
- 替换与追加构建都先写临时集合，成功后再发布；失败构建保留原索引。
  追加时复制已有向量，避免重新计算旧片段。
  同一本教材的构建由进程间文件锁保护；第二个写入者在调用 embedding 前被拒绝。
  发布的前后重命名失败均会回滚并清理临时集合，包括重命名已生效但调用抛错的情况。
- API 队列默认最多接收 8 个请求，包含正在执行的 1 个请求。
  排队使用协程，断开后立即归还容量；正在执行的线程实际退出后才释放执行槽。
  REST 和 SSE 队列满时均在回答启动前返回 HTTP 503。
- 教材目录独立读取，不等待模型执行锁；API 和 Streamlit 能看到新增、删除的教材。
- 全库问答共享一次查询向量；每本教材保留最多 `3 × top_k` 个融合候选，统一重排一次。
  单教材候选预算不变。
- CI 从 `uv.lock` 安装依赖，构建关闭隔离环境中的二次依赖解析。
  新增独立 Chromium 任务，执行原始聊天页的 JavaScript。
- SQLite 目录指纹连接在成功与异常路径上均立即关闭，避免 Windows 删除索引副本失败。
  干净构建环境显式安装锁定的 setuptools / wheel，支持 jieba 的源码构建。
- 本地 reranker 增加 `RAG_QA_RERANK_BATCH_SIZE`，默认保持 32；Worker 也读取此配置。
- 生成评估输出目录增加进程锁，防止两个续跑进程重复生成、交错写入协议与 JSONL。
- 索引构建锁使用固定长度摘要，允许长教材标识；备份集合名遵守 Chroma 的 512 字符上限。
- 检索评估的去重和证据保留以教材与片段编号共同识别来源，不把跨书同编号视为同一片段。
- 追加构建在 embedding 前检查模型兼容性；旧索引没有协议指纹时，也会检查已保存的模型名。
- 新建临时集合使用 `sync_threshold=1`，每批原生日志应用后写入 HNSW 文件。
  这修复了小缓存淘汰未同步索引后无法读取旧向量的问题；现有索引的配置未被迁移。
- reranker 初始化失败时关闭已经打开的索引；兼容的交互式构建与数据库工具也显式关闭客户端。

此前已修复生成前失败的额度退款、跨 UTC 日期退款、空回答完成判断、截断生成评估排除、
跨教材相邻片段去重和 Docker 代理信任默认值。

## 实际推理与 HTTP 验收

使用索引副本、每本教材一题 dev、每条路线 10 个计时样本，包含真正的本地模型推理，
没有复用模型分数。小样本 P95 为最近秩统计，只描述本次运行，不能作为服务 SLO。

| MPS 路线 | 中位耗时（秒） | P95（秒） | 重排片段数 |
|---|---:|---:|---:|
| 基线，单教材，批大小 32 | 0.558 | 0.610 | 15 |
| 当前，单教材，批大小 32 | 0.555 | 0.661 | 15 |
| 基线，全库，批大小 32 | 1.548 | 1.712 | 40 |
| 当前，全库，批大小 32 | 1.978 | 2.366 | 75 |
| 当前，单教材，批大小 8 | 0.402 | 0.508 | 15 |
| 当前，全库，批大小 8 | 1.768 | 1.905 | 75 |

基线与当前的批大小 32 在同次运行中交替计时；批大小 8 是另一次运行，机器负载与温度可能不同。
扩大候选池后的默认全库路线实测约慢 28%，因此这次改动不能描述成已经降低全库延迟。
同一批 75 个候选的重排专项实验比较 8 / 16 / 32 / 64，每种批大小 10 个样本；
中位耗时分别为 1.831 / 1.871 / 2.048 / 2.470 秒，前五名排名均与批大小 32 一致。
这支持按设备调整批大小，尚不支持替所有 MPS 或 CUDA 设备修改默认值。
第一轮完整对照的进程峰值 RSS 约 1551 MiB，覆盖两版引擎和全部路线。
随后对全部 35 道 dev 题逐题比较批大小 8 / 32：单教材与全库各 35 次，前五名顺序全部一致。
这是推理批大小的排序稳定性验收，不能替代独立的跨教材相关性标注。

同样的 40 个计时样本在本机 CPU 上实测：单教材中位耗时由 1.365 秒变为 1.331 秒，
全库由 3.881 秒变为 4.861 秒（约慢 25%）；当前全库 P95 为 6.352 秒。
CPU 运行的进程峰值 RSS 约 4000 MiB，同样不能归因于单条路线。
批大小 8 的独立 CPU 运行中，当前单教材 / 全库中位耗时为 1.009 / 4.547 秒，
全库 P95 为 4.835 秒，进程峰值 RSS 约 3131 MiB；不同运行的内存与耗时仅作描述。

真实 Uvicorn / HTTP 验收使用受控无模型后端：容量 3，8 个并发客户端中 3 个成功、
5 个返回 HTTP 503，峰值执行线程为 1。排队断连释放容量；活跃断连只发取消信号，
执行线程退出前下一条请求保持排队。两种问答端点都在队列满时返回 JSON 503，
健康检查保持可用，队列最终归零，生成额度未消耗。
该脚本已加入六个平台 / Python 组合的 CI；人工后端延迟不能用作检索性能数据。

逐次计时、批大小实验及 HTTP 状态记录保存在
`artifacts/evaluations/serving-performance-20261004/`。

## HNSW 缓存故障复现与修复

Chroma 1.5.9 的 Python 绑定根据文件句柄上限决定索引缓存容量，Windows 默认值为 102；
底层缓存分成 64 份。原生执行器只在集合第一次读取时回放 WAL，后续缓存淘汰不会重新回放。
因此未达到默认同步阈值的索引被淘汰后，文档计数仍在 SQLite 中，而读取向量会报
`Nothing found on disk`。这里依据的是锁定版本的
[缓存配置](https://github.com/chroma-core/chroma/blob/1.5.9/rust/cache/src/foyer.rs)、
[绑定配置](https://github.com/chroma-core/chroma/blob/1.5.9/rust/python_bindings/src/bindings.rs)和
[读取流程](https://github.com/chroma-core/chroma/blob/1.5.9/rust/frontend/src/executor/local.rs)，
并通过本机缩小原生缓存的实验核对。

相同的两个生命周期场景，在本机模拟容量 102 时，修复前第 5 轮失败，随后的两次只读也失败；
修复后连续 100 轮通过，没有读失败后的业务重试。另一个回归场景在容量 64 下构建 131 个小集合，
原集合仍能读取完整向量并查询，新集合的持久化元数据也已写盘。
SQLite 关闭后偶发文件清理失败尚未单独确定根因，CI 保留首次失败与延迟释放诊断。

另用操作系统教材的 1183 个现有片段、固定的 1024 维随机归一化向量，在本机交替构建各 3 次：
阈值 1000 / 1 的中位耗时分别为 3.140 / 0.927 秒，每次均为 37 批。
这是无模型的索引写入实验，本次没有观察到同步配置增加构建耗时；不能推广为真实 embedding
构建或所有设备上的提速结论。结果为 `serving-performance-20261004/index-write-cost-varied.json`。
