# 查询分解：实现与验证记录

状态：已实现，默认关闭。2026-09-13 已完成6道开发题、开关各一次的完整问答回归；不是独立效果评测。当前基线见 [稳定基线](stable-baseline.md)。

## 入口与处理流程

网页侧栏「实验功能（默认关闭）」或 `engine.ask(..., use_decomposition=True)`。
普通问答不经过分解流程；第一版只处理独立子问题，不处理后一问依赖前一问答案的递归多跳检索。

1. 本地检查明确的单一概念、单一原因及明显前后依赖的问题，直接使用原查询。其他情况交给规划模型；该检查不保证识别全部简单题或依赖题。
2. 规划最多3个独立子问题，且不超过 top_k。校验结构、非空、长度和重复；不可用、格式错误、超时或 top_k 不足时恢复原路径。规划温度0、上限500 token、20秒超时、不重试。
3. 保留原问题，在用户选定教材范围分别检索。成功分解时关闭该次 HyDE；各路取 top_k×3 候选，轮流合并并按教材及规范化内容去重，候选总数最多60，再用原问题统一重排一次。
4. 优先选入每个子问题的首选片段，其余位置按统一排名补齐。2000字符上下文预算优先装入首选完整片段，剩余位置按长度装入其他完整片段；必需片段总长超预算时再分配份额。文本按完整句截断并标记省略，表格按完整行保留，无完整句则跳过。
5. 使用原问题和选定证据生成一次答案。记录 `context_sources`，引用展示与评估均使用实际输入片段；`decomposition` 保存状态、子问题及未进入上下文的子问题编号，并要求回答提示相应证据不足。

路由有片段进入上下文只代表检索覆盖，不保证片段足以回答。即使证据完整，模型仍可能补充缺少依据的细节。

## 已验证的修复

- 关键证据截断：原等额预算会截掉进程特征、循环队列取模解释；完整片段优先策略修复了保存的失败案例。最新4道复合题开启组所有选中片段均未截断，不代表全系统所有问题都不会截断。
- 规划延迟：仅对 `api.siliconflow.cn` / `deepseek-ai/DeepSeek-V4-Pro` 的规划请求显式关闭思考，普通答案参数不变。配对试验平均约6.62秒降至1.54秒；随后8次实际调用均成功，约1.32–1.68秒。这确认可避免的思考开销，未证明历史超时的唯一原因。
- 完整问答回归：12/12请求正常结束；开启组2道简单题跳过规划，4道复合题成功分解，规划1.228–1.515秒。平均总耗时关闭26.40秒、开启27.39秒，小样本不支持稳定延迟收益结论。
- 仍未通过：栈/循环队列答案补充了引用片段未说明的递归实现细节；因此继续默认关闭，不声称整体准确率提升。

`data/evaluation/decomposition_routing_dev.json` 的26条样例仅用于路由回归，不是独立评测集。

## 后续验收与回退

先补充有必要证据标注的开发题，固定索引、模型、top_k及上下文预算，比较每个子问题的证据充分性、答案陈述与引用对应、失败率及耗时。留出题不参与方案选择。
简单题出现新增失败，或复合题无收益却增加开销时保持默认关闭。关闭开关恢复普通路径；规划异常自动回退。
