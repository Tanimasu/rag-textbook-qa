# 评测方法与结果

README 只保留怎么跑和必要的配置提醒，口径、依据和已知限制放在这里。
所有结论都注明了适用范围：换了分块、换了 schema、换了预算之后不可直接比较。

## 检索评分口径

相关性按四级评分：标注标题精确匹配记 3 分，同深度且同父节的兄弟小节记 2 分，
有明确章号依据的同章内容记 1 分，其余记 0 分。局部列表编号不能推断章号，父节不算兄弟小节。
这些等级是标题结构的启发式代理，**不代表片段已经包含答案**。

引入分级的原因是失败分析里出现过检索命中 3.5.2 而标注是 3.5.3 的情况，
命中/未命中的二元口径会把它和取到完全无关章节记成同一个结果。

## nDCG

按 chunk 粒度计算：每本书索引中的全部 chunk 按同一规则评分，排序后取 Top-K 作为理想收益。
重复 chunk ID 不重复计分。同一小节的不同 chunk 可以各自获得精确匹配分，分母也包含这些 chunk。
没有候选全集的底层测试调用会标记 `returned_results_only`，只反映返回列表内部排序，
不能与正式 `corpus` 口径比较。

旧版固定理想排名（`[3]*wanted + [2]*top_k`）不是上界，65 题里有 14 到 24 题得分超过 1、
最高 1.607，因此**旧口径的 nDCG 数值及其上的显著性检验全部作废**。
语料理想值依赖分块粒度（一节被切成三块就要求三次精确命中），也会奖励堆叠同一小节的 chunk，
所以只在同一 schema、同一分块下比较。

## 证据保留率

把同一批检索结果按 `--context-budget`（默认 4000 字符，与问答默认值一致）用问答实际的装入逻辑打包，
统计评为精确或兄弟小节的片段里有多少真正进了上下文，其中又有多少被截断。

检索评测只看片段有没有排进 Top-K，RAGAS 只看送进模型之后的上下文，
「检索到了却装不下」这一段原本没有任何指标——两次握手题正是丢在这里。
这一步不调用任何模型，完全确定性。`--context-budget 0` 可只评测检索。

它是代理指标：片段在上下文里不等于答得出来，而且塞更多更短的片段也能把它刷高，
所以要和片段数、上下文字数一起看，并且只在相同预算下比较。下表历史结果使用报告 schema 3。

65 题、Top-5、本机 MPS 实测，同一套检索结果只改预算：

|策略（预算）|Recall@5|证据保留率|送达/取回|丢弃|截断|平均片段数|平均上下文字数|
|---|---:|---:|---:|---:|---:|---:|---:|
|BM25（2000）|0.708|0.779|100/128|28|20|3.69|1716|
|Embedding（2000）|0.815|0.914|160/180|20|21|4.11|1540|
|Hybrid（2000）|0.831|0.900|157/179|22|26|4.12|1607|
|Hybrid+Rerank（2000）|0.923|0.817|154/191|37|23|4.03|1601|
|Hybrid+Rerank（3000）|0.908|0.937|179/190|11|17|4.78|2128|
|Hybrid+Rerank（4000）|0.923|1.000|191/191|0|4|5.00|2336|

保留率是逐题平均，只在「Top-K 里确实有相关片段」的题上有定义，四种策略的分母分别是
51、57、58、62 题，所以跨策略不可直接比；「送达/取回」是全部 65 题的合计，才是可比的那一列。

**默认预算下排序最好的策略送达的证据反而最少**：Hybrid+Rerank 取回 191 条相关片段而
Embedding 取回 180 条，装进上下文后却是前者 154 条、后者 160 条。Recall@5 数的是排进前五，
2000 字符平均只装得下 4 条，排在第 4、5 位的相关片段会被丢掉；重排把更多相关片段挤进前五，
也就有更多片段挤在预算边界之外。预算提到 4000 后 191 条全部送达、截断从 23 条降到 4 条，
而平均上下文字数只从 1601 涨到 2336——多数题目的 Top-5 本来就不到 4000 字符，
2000 正是实际卡住的那一刀。

**据此把默认预算改为 4000**（2026-09-15，`DEFAULT_CONTEXT_BUDGET`）。依据只有上面这份证据保留率，
是确定性的；**"送达更多片段能否提高答案质量"仍未验证**。代价是每次回答的上下文变长、token 上升，
并且此后的 RAGAS 分数与 2026-09-15 之前的运行不可比。上表仍按各自标注的预算读。

预算不参与检索，所以 3000 那一行的 Recall@5 0.908 不是预算造成的，而是下面那条重排抖动又出现了一次。

## 标注正文覆盖

标题层级只能判断“到了哪一节”，不能判断返回片段是否包含回答所需的正文。产品验收中曾出现
Top-5 命中 `3.1.2 三个基本问题`，但只取到解释透明传输问题的前半段；真正说明 ESC 字节填充的
紧邻片段没有取回。章节 Recall 把它记为成功，实际交给模型的证据却不完整。

带有 `evidence.path/start_line/end_line/sha256` 的题目现在额外计算标注正文覆盖：先核对整个教材文件
的 SHA-256，再读取审核时冻结的行段；正文与 Top-K 片段分别去除空白、标点和 Markdown 格式，按
16 字符连续片段计算覆盖比例。报告同时记录检索覆盖和上下文送达覆盖，不把教材正文复制进结果文件。
没有正文标注的旧题集继续只输出原有章节指标。

这个指标比章节命中严格，但仍不是“关键答案覆盖”：一段审核行段可能包含背景、例子和答案，覆盖率低
不一定不能回答，覆盖率高也不保证模型正确使用证据。它用于发现章节命中造成的假阳性和上下文截断，
不能代替人工核对或生成质量评测。加入该指标后检索报告 schema 为 4；旧 schema 3 报告仍可读取，
但两种 schema 的正文覆盖字段不可混用。

## 同小节相邻块补充实验

透明传输题的失败表明，答案可能恰好跨越分块边界。为避免针对已复核的产品验收题做定向修补，
相邻块方案只在 35 题 dev 划分上选择，未查看 holdout 的本实验结果，也没有调用回答模型或评判 API。
实验固定 Hybrid + Reranker、Top 5 和 4,000 字符预算，比较三种上下文装入顺序：

- 原始 Top 5；
- 原始结果全部优先，剩余预算再补同一完整标题路径下的后一块、前一块；
- 每个原始结果后立即插入同小节邻块。

Windows CUDA Worker 上独立运行三次，三次逐题 Top-5 排序和下表指标完全一致：

|装入方案|平均章节正文覆盖|相对基线|提升 / 回退题数|原始来源保留率|平均上下文长度|
|---|---:|---:|---:|---:|---:|
|原始 Top 5|0.5677|—|—|1.0000|2821|
|原结果优先，再补邻块|0.5895|+0.0218|8 / 0|1.0000|3194|
|邻块插队|0.5715|+0.0037|8 / 6|0.9257|3194|

离线 BM25 预实验也得到相同方向：原结果优先方案提升 0.0375，12 题提升、0 题回退并保留全部原始
来源；插队方案会挤掉原片段。由此淘汰插队方案。原结果优先方案现已作为默认关闭的实验开关接入，
**产品默认路径仍未改变**：章节正文覆盖仍是结构代理指标，不代表回答一定更忠实。下一步应用未参与
选择的材料和生成质量指标验收，而不是直接在已经看过的 holdout 上继续调规则。

实验可由 `scripts/experiment_adjacent_context.py` 复现。脚本会核对向量库与当前 chunks 产物的 ID
集合完全一致，强制关闭远程失败后的本地回退，并把原始报告写入 Git 忽略的本地评测目录。

## 含重排的结果跨进程不完全可复现

同一进程内重复检索逐位一致；五次独立进程运行中，BM25、Embedding、Hybrid 三种策略逐题 Top-5
章节完全相同，只有 Hybrid + Reranker 在汉明码一题上换掉一个片段，使 65 题 Recall@5 在 0.877
与 0.892 之间变动（五次中两次为 0.877），幅度约一道题。

实测被交换的两个候选重排分差约 0.05，并非近似并列，所以早先归因于 MPS 浮点微差的说法不成立；
引擎按 `sorted(terms)` 安装挖掘出的 BM25 词条，也排除了 jieba 插入顺序。**具体原因尚未定位**，
解读任何含重排的结论时都须考虑这一抖动。

## 差异要用配对检验

各策略跑的是同一批问题，差异也比看上去小，所以必须用配对检验，不能对比两个均值就下结论。
65 题上（标注修正之前）只有「Hybrid + Reranker 优于纯 BM25」达到显著（分歧 15 题，1:14，p=0.0010）；
重排相对不重排仅 2:7（p=0.18），纯向量与融合为 2:2（p=1.00）。

按当时比例外推，要让重排的优势显著需要约 108 题。更早一次从 50 题外推预测 56–64 题即可，
结果是错的——新增的题改变了分歧比例，所以这类外推只能当下界，不能当计划。

## 分词与融合权重

两者都是用这套评测调出来的。

BM25 原先直接用 jieba 默认词典，而它会把教材术语切碎：散列表切成「散 / 列表」，
冯诺依曼切成「冯诺 / 依曼」，十二个抽样术语里十一个被切开。BM25 在本系统里的职责恰恰是
精确命中术语，所以这等于让它带伤工作。现改为词 + 字符二元组混合分词并过滤标点空白；
二元组不依赖词典，词典没见过的术语只要查询写法一致就能命中。四种方案对比：纯 jieba 与
仅加领域词典均为 Recall@5 0.600，纯二元组 0.700 但会拖低融合后的召回，
词 + 二元组混合取得 0.700 且融合表现最好。

融合权重在 50 题标注集上重新扫描后，BM25 定为 0.5。开启重排时（系统默认配置），
Recall@5 在 0.4 到 0.6 之间稳定为 0.900，两侧都会下滑，因此取该平台中部。
BM25 确实在起作用：权重归零时重排后的 Recall@5 掉到 0.820，相当于四道题，
而分词修好之前它只值一道题。

## 标注集的由来与污染范围

现为 65 题，按教材分层切成 dev 35 与 holdout 30。问题文本复用 `test_questions.json` 里
人工撰写的题，仅由模型补充「答案位于哪一节」的标签，并排除被误当作正文的目录条目。

**检索评测集必须使用人工措辞的问题。** 曾尝试让模型依据小节原文直接出题，
但那样生成的问题会沿用原文用语，BM25 按字面匹配就能不经理解而命中：
同一系统上，模型据原文生成的题使 BM25 的 Recall@5 虚高到 0.975，人工措辞的题只有 0.680，
而向量检索几乎不变。

新增的 15 道 holdout 题经过 v1 到 v4 四轮修订后并入主标注集：v2 修正证据章节并替换 3 题，
v3 替换 3 题被分块器误提升为标题的正文列表项标注，v4 改写 4 题措辞，把字面重合度中位数
从 0.394 降到 0.345，接近人工 50 题的 0.319。各版 JSON 与审核记录保留在
`data/evaluation/retrieval_holdout_candidates_v{1..4}.json` 及同名 `.md` 中以供追溯。

**已知污染**：当前的融合权重是在切分之前用全部 50 题扫出来的，因此 holdout 里较早的 15 题
对该参数并不干净，今后停止用它们调参也不能消除已经发生的信息泄漏——这 15 题只能作为
历史验证子集，不能支持独立泛化结论。后加的 15 题没有参与过任何调参。

2026-09-14 修正了两道数据库开发题的章节标注，此后 dev 的 hybrid-rerank Recall@5 为 35/35，
dev 已无法再体现召回提升，只有 MRR 和 nDCG 还能动。那次审核只检查了未命中的题，
可能单向移动分数；下次重新标注前应同样抽查一批已命中的题。详见
[数据库证据复核](database-evidence-review.md)。

## RAGAS 验收标准

RAGAS 是验收指标，不是优化目标：一轮耗时一小时以上且消耗 token，分数又混合了检索、提示词与
生成模型三者，单项涨跌无法归因。检索改动应在确定性的检索评测上迭代，RAGAS 只在阶段末尾跑一次
确认方向。下列标准是在看到该轮数字**之前**约定的，这是验收和事后解释的唯一区别：

- **Faithfulness 优先。** 教材问答场景下，不编造内容比相关性更重要。提示词要求模型在资料不足时
  明说，而 RAGAS 会把这种诚实拒答的 Answer Relevancy 直接判为 0，两项指标结构上对立。
  因此以相关性下降换取忠实度提升，判定为通过。
- **其余三项容忍 0.03 的回退。** 该数值为暂定。之后对同一系统跑了两轮 RAGAS，逐题平均绝对差为
  Faithfulness 0.10、Context Precision 0.06、Answer Relevancy 0.10、Context Recall 0.12；
  0.03 的门槛是按噪声放宽还是改为多轮平均，尚待决定。
- **绝对下限尚未约定。** 下次触发权衡判定时一并确定。

RAGAS 的上下文使用实际发送给生成模型的文本，质量均分仅覆盖成功问题。每次运行额外输出
`ragas_run_summary.json`，记录总题数、成功率及失败原因类别（只记异常类名，不记错误文本）；
即使全部问题失败也会保留摘要。该口径与旧版评估不同，**不宜直接比较历史分数**。
