# 工程决策与排障记录

这页挑出做这个系统时最有代表性的十一次判断，每条都写四件事：问题怎么暴露、靠什么证据、最后改了什么、
代价和还没解决的部分。数字都来自链接里的原始记录，适用范围以原文为准；这里只做索引和提要。

## 1. 检索结果在进程之间抖动 → 改用精确向量检索

**现象**：同一份索引、同一道题，Hybrid + Reranker 在不同进程里会换掉一个片段，65 题 Recall@5 在
0.908 和 0.923 之间跳；其余三种策略逐题稳定。早先怀疑过 MPS 浮点误差和 jieba 词条顺序，都被排除。

**排查**：8 组对照、每组 3 个独立进程，每次记录送进重排的候选（顺序、ID、正文哈希）和全部重排分。
共同候选的重排分组内差值全为 0，分歧出在重排之前的语义候选；用保存下来的同一个查询向量直接调 Chroma，
不经过嵌入、分词和重排，仍能复现。最后查到计算机组成那本书的索引有 245 条记录只在日志里、没进持久化的
向量图，每个进程启动时 Chroma 把它们并行插回图，图结构每次不同，深层的近似检索结果也跟着变。

**决定**：五本书只有约 5700 个 1024 维向量，近似检索在这个规模上没有必要。0.3.41 改为在缓存的归一化
矩阵上做精确余弦搜索：向量与 BM25、语料在同一次刷新、同一把锁下整体替换；点积用固定次序累加、不依赖
BLAS 线程数，同分按 chunk ID 排序。Chroma 继续负责存储和发布，产品检索不再查询它的近似索引。

**结果与边界**：65 题四种策略在 5 个独立进程中逐题一致；dev 35 题与三个旧基线相比 Top-5 零变化。
全库语义阶段中位数 29.27 → 9.66 毫秒，但端到端中位数略慢（1.933 → 1.994 秒，差值主要在模型阶段）；
矩阵常驻 22.27 MiB，整体刷新多约 0.15 秒。没有修补 Chroma 本身，CPU/CUDA 上的真实模型确定性未验证。

详见 [跨进程抖动的根因与修复](evaluation-methodology.md#跨进程抖动的根因与修复)、
[精确向量检索的性能记录](retrieval-performance.md)。

## 2. 排序最好的策略送达的证据反而最少 → 新增证据保留率，上下文预算改为 4000 字

**现象**：检索评测只看相关片段有没有排进前五，RAGAS 只看送进模型的上下文，中间“检索到了却装不下”这一段
没有任何指标。一道关于“两次握手”的题正是丢在这里。

**证据**：按问答实际的装入逻辑重放同一批检索结果。2000 字预算下，Hybrid + Reranker 取回 191 条相关片段、
只送达 154 条，纯向量取回 180 条反而送达 160 条：重排把更多相关片段挤进前五，也就有更多片段落在预算边界
之外。预算提到 4000 后 191 条全部送达，截断从 23 条降到 4 条，平均上下文只从 1601 字涨到 2336 字。

**决定**：默认预算改为 4000 字（2026-09-15）。这个指标完全确定、不调用模型，可以无人值守地反复跑。

**边界**：它是代理指标，塞更多更短的片段也能刷高，必须和片段数、上下文字数一起看；
“送达更多片段能否提高回答质量”没有验证。详见 [证据保留率](evaluation-methodology.md#证据保留率)。

## 3. BM25 把教材术语切碎 → 词加字符二元组混合分词

**现象**：jieba 默认词典把“散列表”切成“散 / 列表”，“冯诺依曼”切成“冯诺 / 依曼”，十二个抽样术语里
十一个被切开。BM25 在系统里的职责恰恰是精确命中术语。

**证据**：纯 jieba 和只加领域词典的 Recall@5 都是 0.600；纯二元组 0.700，但会拖低融合后的召回；
词加二元组混合同样 0.700，而且融合表现最好。修好分词后，BM25 权重归零会让重排后的 Recall@5 掉约四道题，
修之前它只值一道题。

**决定**：词与二元组混合分词，并从教材自己的各级标题里挖术语。分词器私有，索引和查询共用同一份，
不改动全局 jieba 状态。详见 [分词与融合权重](evaluation-methodology.md#分词与融合权重)。

## 4. 两路分数不能直接相加 → 加权倒数排名融合

余弦相似度和 BM25 分数尺度完全不同，直接加权求和等于让分数范围大的一方说了算。融合改为按名次计分
（`权重 / (60 + 名次)`），向量 1.0、BM25 0.5。BM25 权重在 0.4～0.6 之间开启重排的 Recall@5 都稳定在
0.900，于是取平台中部。同一片段按教材加正文去重，同分保持先出现的顺序，结果可复现。

代价是这组权重扫描发生在划分 dev / holdout 之前，所以 holdout 里较早的 15 题对它不干净，只能当历史验证子集。
详见 [标注集的由来与污染范围](evaluation-methodology.md#标注集的由来与污染范围)。

## 5. 评测集本身也会骗人

- **模型出的题偏袒 BM25**：让模型照着小节原文出题，问题会沿用原文用语，BM25 的 Recall@5 虚高到 0.975；
  同一系统上人工措辞的题只有 0.680，向量检索几乎不变。所以检索评测只用人工措辞的问题。
- **旧 nDCG 的理想值不是上界**：固定理想排名下，65 题里有 14～24 题得分超过 1，最高 1.607。旧口径的数值和
  其上的显著性检验全部作废，改为按每本书全部片段计算理想值。
- **差异要用配对检验，外推不能当计划**：从 50 题外推“56～64 题就能让重排的优势显著”，加题后被推翻，
  新题改变了分歧比例。

详见 [评测方法与结果](evaluation-methodology.md)。

## 6. 评判模型先校验再使用 → 校验没过就不用

做按采样的生成评测前，先拿 30 份已经逐题审查过的回答检验评判器，并预先登记门槛 AUC ≥ 0.70。
实测 AUC 0.598：评判器很稳定（重判差 0.017），审查标出的问题 14 份里找到 13 份，但它逐条计数的口径和
审查“只标实质问题”的口径不同，给回答的排序对不上。按规定暂停温度对照，没有发出任何生成请求。
稳定不等于有效。详见 [评判器校验](generation-judge-validation-20260915.md)。

## 7. 远程 Worker 离线时每个问题等两分半 → 连接单独限时，失败后冷却

**现象**：Embedding 和 Reranker 可以交给 Windows GPU Worker。对端离线时，连接和等待结果共用 120 秒超时，
macOS 要等系统约 75 秒才放弃连接，开启回退时每个只检索的问题约 150 秒。

**决定**：连接单独限时（默认 5 秒）；一次瞬时故障后 60 秒内直接用本地模型，到期再试远程，Embedding 和
Reranker 共用这份记录。认证失败、模型指纹不一致和协议错误仍直接报错、不触发冷却；建索引和评测从不回退。

**结果**：第一题 12.3 秒，随后每题 0.6 秒。详见 [版本记录 0.3.37](release-notes.md)、[远程 Worker](remote-worker.md)。

## 8. SDK 重试叠在项目重试里 → 只保留一层

用真实 SDK 和隔离的 503 响应复现：非流式设 `retry=1` 本应最多请求两次，实际六次；默认 `retry=2` 可能到九次。
原因是 SDK 自带的两次重试叠加在项目重试之内。项目自建的 SDK 改为关闭内置重试；401 / 422 这类永久错误
立即失败，429 和 5xx 才在既定次数内重试，不完整的回答不重试。
详见 [防止 SDK 放大重试次数](iteration-20261007-remote.md#防止-sdk-放大重试次数)。

## 9. 索引更新时，读者不能看到半新半旧的结果

- **发布**：每本书一个跨进程写锁，先写进私有的临时集合，全部批次成功才发布；追加也不再逐批改动可见集合。
- **读取**：用只读 SQLite 计算发布版本摘要。引擎在检索前后各核对一次版本，变了就整体重建 BM25、向量、
  阅读等缓存并重试，最多三次；绝不把新的语义结果和旧的关键词或阅读缓存混在一起。
- **一个 Chroma 缓存故障**：Windows 上原生缓存容量只有 102，日志只在集合第一次读取时回放；没同步的索引被淘汰后，
  再读向量会报 `Nothing found on disk`。复现时第 5 轮失败，改为每批写入都同步持久化后连续 100 轮通过。

详见 [HNSW 缓存故障复现与修复](optimization-20261004.md#hnsw-缓存故障复现与修复)、[开发说明](development.md)。

## 10. 更快但会改变排名的设置，不进默认值

- **重排批大小**（0.3.39）：MPS 上批大小从 32 改为 8，全库检索中位数 3.250 → 2.789 秒（约 −14%），
  dev 35 题和 65 题的候选池、Top-5 都零变化，于是改为默认。
- **截断长度和半精度**：长度 384 会改变单本 23 / 35 题的排名，float16 改变 4 / 35 题，只做成默认关闭的开关。
- **关闭回答前的隐藏推理**（0.3.36）：首字 18.7 → 1.1 秒，整段 30.7 → 9.7 秒，输出 token 1232 → 376；
  但回答质量没有评测，所以只是可选项，且只对已验证的服务和模型组合发送该参数。

详见 [本机检索与重排性能](retrieval-performance.md)、[版本记录](release-notes.md)。

## 11. 不掩盖教材自相矛盾

数据库教材在 UNIQUE 约束允许几个 NULL 这一点上前后说法不一致。系统登记这处已核实的矛盾：只有两侧原文都
进入实际送给模型的上下文时，才要求回答并列给出两种说法。没有提示不代表教材在这一点上没有矛盾，
`rag-qa index check` 只验证已登记的条目仍能在索引中找到。详见 [使用手册](usage.md#当前行为与已知限制)。

## 还没解决的

- **当前版本的回答质量没有重测**：README 的 RAGAS 表是 2026-03 的历史运行；关闭推理后的回答质量也没测。
- **检索评测在 dev 上已经饱和**：默认路线 dev 35 题全部命中，剩下 6 个漏检都在 holdout，而 holdout 不能拿来调参。
  继续改进检索需要新的开发题。
- **跨教材回答质量**只有开发集代理检查，缺独立标注与验收。
- **引用编号能对上，不等于每句话都有原文支撑**；教材冲突保护只覆盖一处已核实的矛盾。
